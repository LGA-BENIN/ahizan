# 2. Analyse Comparative : AHIZAN V1 vs Standard Vendure v3

### A. Modèle Vendeur & Multi-Boutique

| Aspect | Implémentation Actuelle (AHIZAN V1) | Standard Officiel Vendure v3 |
| :--- | :--- | :--- |
| **Entité Vendeur** | Création d'une entité sur mesure `Vendor` avec 40+ champs (KYC, RCCM, Wallet, Coordonnées GPS). | Utilise l'entité native `Seller`. Les informations spécifiques (RCCM, KYC, Wallet) s'ajoutent via `customFields` sur `Seller`. |
| **Isolation Multi-tenant** | Le vendeur est relié aux produits via un custom field de relation : `product.customFields.vendorId`. | **1 Vendeur = 1 `Seller` = 1 `Channel` dédié**. Chaque vendeur opère dans son canal avec son token (`vendure-token: <slug-du-vendeur>`). |
| **Filtrage des données** | Requêtes personnalisées (`myVendorProducts`) qui filtrent manuellement en base avec des jointures SQL. | **Isolation automatique native** : Vendure filtre automatiquement les produits, stocks, prix et commandes selon le `Channel` du `RequestContext`. |

### B. Gestion des Produits, Variantes et Catalogue

| Aspect | Implémentation Actuelle (AHIZAN V1) | Standard Officiel Vendure v3 |
| :--- | :--- | :--- |
| **Création de Produit** | Mutation custom `createMyProduct` + injection SQL directe dans les tables de jointure (`product_channels_channel`, `product_variant_price`, etc.). | Utilisation des mutations natives `createProduct` / `createProductVariants` exécutées dans le contexte du canal vendeur (`ctx.channel`). |
| **Événements & Réindexation** | Les écritures SQL directes contournent l'`EventBus` Vendure. | Les services natifs émettent automatiquement `ProductEvent`, déclenchant l'indexation de recherche (`SearchService`), le cache et les webhooks. |
| **Champs Personnalisés** | Très bonne utilisation de `customFields` sur `ProductVariant` (`compareAtPrice`, `promotionalPrice`, `onPromotion`) et `Product` (`shortDescription`). | Conforme aux recommandations Vendure. |

### C. Gestion des Commandes & Panier Multi-Vendeurs

| Aspect | Implémentation Actuelle (AHIZAN V1) | Standard Officiel Vendure v3 |

# 3. Points forts & Risques identifiés

###  Ce qui est déjà bien conçu
1. **L'utilisation des Custom Fields** : L'implémentation dans `vendure-config.ts` (`Address`, `ProductVariant`, `Collection`) est propre et respecte les conventions Vendure.
2. **Les calculateurs de livraison & d'éligibilité** : `GeoEnginePlugin` s'intègre via `ShippingCalculator` et `ShippingEligibilityChecker`.
3. **Le découpage frontend/backend** : Storefront, Seller et Auth sont clairement modularisés en Next.js.

### ⚠️ Risques et limites de la surcouche actuelle
1. **Bypasses SQL directs (`rawConnection.query`)** :
   - Risque de rupture de cohérence transactionnelle.
   - Perte des hooks d'événements Vendure (ex : l'index de recherche ne se met pas à jour tout seul lors d'un `INSERT INTO product_channels_channel`).
2. **Double gestion `Vendor` vs `Seller`** :
   - `Seller` est l'entité que Vendure comprend pour la facturation, les canaux, les commissions et les exports comptables. Avoir une entité `Vendor` parallèle crée une duplication de responsabilité.
3. **Maintenance lors des montées de version** :
   - Toute mise à jour majeure de Vendure (ex : v3.x -> v3.y) risque de casser les requêtes SQL injectées directement dans les tables internes de jointure.
